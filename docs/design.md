# 설계와 검증

## 구성

- `EpostClient`: 입력 검증, 요청 스냅샷, 작업 키와 예외 분류, 복구 API.
- `OperationStore`: 영구 기록과 계정 잠금의 계약. 기본 구현은 로컬 SQLite.
- `KoreaPostWeb`: 독립 브라우저 세션, 로그인, 접수·조회·취소.
- `PageFlow`: 우체국 DOM과 페이지 함수에 의존하는 내부 구현. 공개 API와 분리.
- 배치 실행기: CSV/JSON 정규화, 전체 입력 검사, 고정 행 ID, 순차 실행과 보고서.
- CLI: 공통 설정·환경변수, 입력 검사·진단·진행률·결과 내보내기.

기존 서비스의 프레임워크, 주문 모델, 다른 택배사 연동, DB 암호화 서비스와 배포 설정은 포함하지 않았습니다. 사이트 연동에 필요한 기존 로직을 추출하고 업무 상태 관리를 새로 구성했습니다.

## 트랜잭션 범위

SQLite 트랜잭션은 짧은 로컬 변경만 묶습니다. 네트워크를 기다리는 동안 DB 트랜잭션을 열어 두지 않습니다. `running → submitted`를 디스크에 커밋한 뒤 브라우저 변경을 시작합니다. 카드 검증과 임시 받는 분 추가도 이 경계 뒤에 수행하므로 실패를 보수적으로 다룹니다.

외부 시스템은 로컬 트랜잭션에 참여하지 않습니다. 원격 성공 후 프로세스가 종료되어 로컬 성공 기록을 남기지 못하는 구간은 제거할 수 없습니다. 이 구간에서는 자동 재시도를 막고 실제 사이트를 대조합니다. 자동 롤백 목적으로 취소를 실행하지 않습니다.

계정 잠금에는 TTL이 없습니다. 느린 브라우저가 아직 접수 중인데 잠금만 만료되는 문제를 피합니다. 조회용 잠금은 별도로 관리하여 `unknown` 작업의 예약을 확인할 수 있고, 살아 있는 접수 세션과 조회 세션이 충돌하지 않게 합니다. 종료된 읽기 전용 프로세스의 잠금만 회수할 수 있습니다.

## 주문 시스템 연동 예시

1. 주문 DB 트랜잭션에서 주문의 `접수 요청됨` 상태, 고정 작업 키, outbox 이벤트를 함께 저장합니다.
2. 워커가 이벤트를 읽고 `client.reserve(request, { idempotencyKey })`를 호출합니다.
3. 성공하면 별도의 주문 DB 트랜잭션으로 예약번호와 처리 완료를 저장합니다.
4. DB 저장만 실패하면 같은 키로 결과를 다시 받습니다. `OUTCOME_UNKNOWN`이면 주문을 `확인 필요`로 바꾸고 재접수를 멈춥니다.

다중 서버 운영은 기본 SQLite 구현의 범위 밖입니다. `OperationStore`를 교체한다면 키 유일성, 계정 잠금, 제출 전 영구 기록, 조건부 상태 전이, 살아 있는 실행 주체의 잠금 보호를 그대로 구현해야 합니다. 현재 저장소 인터페이스는 동기식이므로 비동기 원격 DB를 직접 연결하려면 별도의 인터페이스 확장이 필요합니다.

## 검증 범위와 남은 한계

단위 테스트는 중복 키, 다른 요청 충돌, 프로세스 간 잠금, 강제 종료 후 잠금 유지, 저장 실패, 결과 복구, 개인정보 비포함, 입력 검증을 확인합니다. Chromium 통합 테스트는 오프라인 가상 페이지에서 실제 DOM 입력과 취소·접수 흐름, 일시적 오류, 중복 POST 차단을 실행합니다.

합성 화면은 사이트 계약을 모델링한 것이며 실제 우체국 HTML 스냅샷이 아닙니다. 공개 버전의 실제 계정 로그인, 카드 인증, 접수 및 취소 호환성은 아직 확인하지 않았습니다. 우체국이 요구하는 추가 인증을 우회하는 기능은 없습니다. 한 예약에 여러 소포 묶기, 부분 취소, 다중 장비, 자동 사후 대조는 추후 별도 설계가 필요합니다.

브라우저 세션은 매 건 독립 context를 생성·종료합니다. 단건은 browser도 종료하며, 배치에서는 browser 프로세스를 재사용하고 배치 종료 시 닫습니다. 작업 기한을 넘기면 단순히 호출자에게 timeout만 반환하지 않고 브라우저를 닫아 백그라운드 제출이 계속되지 않게 합니다. [Playwright Browser API](https://playwright.dev/docs/api/class-browser#browser-new-context)

## 배치의 트랜잭션과 재시도

배치 전체는 하나의 트랜잭션이 아닙니다. 모든 입력을 먼저 검사한 뒤 각 행을 기존 단건 클라이언트로 처리합니다. 앞선 성공 건은 뒤의 실패와 무관하게 유지합니다. 배치 ID와 행 ID로 작업 키를 만들고 정규화한 요청 지문을 비교하므로 순서가 바뀌어도 기존 성공은 재사용되며 다른 입력으로 키를 재사용하면 충돌합니다.

`failed`는 제출 전 실패 또는 운영자가 미접수를 확인한 기록입니다. 명시적 `retryFailed`가 있으면 `claim`의 한 SQLite 트랜잭션에서 지문·상태·읽기/쓰기 잠금을 확인하고 기존 작업을 `running`으로 바꿉니다. 재시도 이벤트를 남깁니다. `running`, `submitted`, `unknown`은 재획득하지 않으며 성공 이력도 변경하지 않습니다.

결과 파일은 첫 원격 요청 전에 저장하고 각 행 처리 후 임시 파일에 쓰기·fsync·rename으로 교체합니다. 저장 실패 시 다음 행을 멈춥니다. 결과 파일과 journal은 분산 트랜잭션으로 묶이지 않으며 journal이 기준입니다. 프로세스/전원 장애 후 결과 파일이 누락되거나 이전 스냅샷이어도 journal을 유지한 채 재실행하면 완료 건을 재사용합니다.

배치 테스트는 전체 사전 검사, 순서 변경 후 재개, 안전한 실패만 재시도, 불확실한 결과에서 중단, Ctrl+C에 해당하는 건 사이 중단, 출력 실패, 스냅샷 격리, 한국어 CSV·기본값·CSV 수식 이스케이프를 확인합니다. Chromium fixture는 한 browser를 재사용하면서 매 건 context를 격리하는 흐름도 실행합니다.

## 미리보기와 복구 안내의 읽기 경계 (0.3)

SQLite 읽기 전용 모드와 `query_only`를 사용합니다. 로컬 점검 명령은 스키마 생성·권한 변경·키 등록·잠금 회수를 하지 않습니다. DB가 없는 경로도 생성하지 않습니다. 여러 입력과 계정 잠금을 하나의 읽기 트랜잭션에서 확인해 일관된 스냅샷을 만들고 즉시 끝냅니다. 실제 실행 시 기존 쓰기 트랜잭션으로 다시 검사합니다. [Node.js SQLite readOnly](https://nodejs.org/download/release/v22.12.0/docs/api/sqlite.html).

중복 탐지는 계정·작업 종류·정규화한 요청의 해시를 비교합니다. 원문 개인정보나 지문을 미리보기 응답에 내보내지 않으며 과거 작업 ID·상태만 경고에 포함합니다. 여러 상자 발송일 수 있어 자동 병합하거나 취소하지 않습니다.

배치 간격은 실제 요청이 끝난 시각부터 다음 요청까지 적용하며 성공 재사용 행은 간격을 소비하지 않습니다. 미리 읽은 완료 상태만 믿고 결과를 반환하지 않고, 기존 claim에서 입력 지문과 최신 상태를 다시 확인합니다. 간격 대기 중 중단하면 다음 키를 아직 획득하지 않았으므로 실패 기록을 새로 만들지 않습니다.
