# 오류와 복구

[문서 홈](README.md) · [배치 재개](batch.md#중단과-재개)

## 상태 전이

```text
running ── 제출 전 오류 ──> failed (잠금 해제)
   │
   └─ 영구 기록 저장 ──> submitted
                            ├─ 외부 결과 확인 + 기록 저장 ──> succeeded (잠금 해제)
                            └─ 오류 또는 결과 불명 ──> unknown (잠금 유지)
```

프로세스가 강제 종료되면 `running` 또는 `submitted`가 남을 수도 있습니다. 자동 만료나 재접수는 없습니다. `submitted`는 최종 예약이 완료되었다는 뜻이 아니라, 임시 목록 추가·카드 검증 등 외부 변경을 시작할 수 있는 경계를 지났다는 뜻입니다.

## 오류별 다음 행동

| 코드                | 의미와 다음 행동                                                                                                    |
| ------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `VALIDATION`        | `field`의 입력 형식을 수정합니다. 값 자체는 오류에 포함되지 않습니다.                                               |
| `AUTHENTICATION`    | 로그인 정보와 추가 인증 필요 여부를 우체국 화면에서 확인합니다.                                                     |
| `EXISTING_DRAFT`    | 본인이 작성 중인 우체국 받는 분 목록을 확인합니다. SDK는 삭제하지 않습니다.                                         |
| `NOT_CANCELABLE`    | 전체 취소 불가. 사이트에서 각 소포 상태를 확인합니다.                                                               |
| `NOT_FOUND`         | 지정한 예약을 찾지 못했습니다. 번호와 로그인 계정을 확인합니다.                                                     |
| `KEY_CONFLICT`      | 이미 사용한 키에 다른 요청입니다. 원래 요청/주문 연결을 확인합니다.                                                 |
| `ACCOUNT_BUSY`      | 같은 계정 작업이 실행 중이거나 확인 대기 중입니다. 완료를 기다리거나 기록을 점검합니다.                             |
| `OPERATION_FAILED`  | 해당 키의 제출 전 실패 또는 미접수 확인 이력이 있습니다. 원인을 해결하고 같은 입력에 `--retry-failed`를 지정합니다. |
| `OUTCOME_UNKNOWN`   | 재시도 금지. 실제 예약 내역을 확인하고 아래 복구 절차를 따릅니다.                                                   |
| `STORAGE`           | 저장소 접근/용량/권한을 점검합니다. 저장소를 지워서 우회하지 않습니다.                                              |
| `RECOVERY_REQUIRED` | 수동 복구의 확인값이 없거나 원래 프로세스가 아직 살아 있습니다.                                                     |
| `PROVIDER_FAILURE`  | 화면 구조 변경이나 사이트 처리 오류 등입니다. 제출 이후라면 클라이언트가 `OUTCOME_UNKNOWN`으로 바꿉니다.            |

## 복구 도우미

```sh
# 진행 중·제출 중·결과 불명 작업을 모아서 보기
node bin/epost.js recovery --env-file .env --limit 20
# 특정 작업의 상태와 다음 확인 절차
node bin/epost.js recovery batch:reserve:shipping-001:order-001 --env-file .env
```

실행 때 별도 `--config`나 `--journal`을 썼다면 동일하게 지정하세요. 사이트 접속 없이 journal을 읽기 전용으로 열며, 계정 ID만 필요합니다. 기록이 없는 경로에 새 파일을 만들지 않습니다. 전체 미해결 개수와 최대 100건의 안내를 제공하고, 일부만 표시하면 `truncated: true`를 반환합니다. 일반 history의 최근 작업 범위와 별도로 미해결 상태를 검색합니다.

특정 키를 넣으면 완료·실패 건의 재사용/재시도 안내도 제공합니다. 원래 프로세스가 살아 있는 `running/submitted` 작업은 기다리도록 안내합니다. 다른 호스트나 프로세스 확인 오류로 종료를 입증할 수 없는 경우도 잠금을 해제하지 않습니다. 프로세스 상태는 조회 순간의 정보이므로 실제 복구 시 다시 검증합니다.

작업 키는 해시로 저장되어 목록에서 원래 키를 복원하지 못합니다. [배치 미리보기](preview.md)나 원래 입력의 배치 ID·행 ID로 키를 확인하세요. 도우미는 사이트 결과를 자동 판정하거나 복구를 실행하지 않습니다. 아래 실제 대조 절차를 거쳐 `resolve`를 사용합니다.

## 수동 복구

1. `operation 작업키`로 현재 상태를 읽습니다. 원래 실행 프로세스와 남은 브라우저가 완전히 종료되었는지 확인합니다.
2. 같은 계정으로 우체국 사이트에서 발송인, 수취인, 방문일, 내용품과 예약번호를 원래 요청과 대조합니다. 카드 처리와 임시 목록도 확인합니다. 단순히 조회 결과가 비었다고 미접수로 확정하지 않습니다.
3. 실제 접수를 확인했다면 `examples/resolution.json` 형식의 파일에 **확인한** 번호와 상태를 적습니다. 취소 작업은 `status: "canceled"`여야 하며 원래 취소 대상 번호와 일치해야 합니다.
4. 확인한 결과로 기록을 복구합니다.

```sh
node bin/epost.js resolve order-001 --result verified-result.local.json --verified --env-file .env
```

실제로 접수되지 않았음을 확인했고 남은 임시 목록도 정리했다면:

```sh
node bin/epost.js resolve order-001 --not-submitted --verified --env-file .env
```

`--verified`는 실제 사이트 대조와 원래 프로세스 종료를 운영자가 확인했다는 명시적 선언입니다. SDK가 요청의 수취인과 입력된 예약번호를 자동으로 연결해서 검증하는 기능은 아닙니다. 잘못된 번호를 입력하지 마세요.

성공 복구 후 원래 키를 다시 호출하면 저장한 결과를 반환합니다. 미접수 복구 후에는 원래 키가 `failed`로 남습니다. 동일한 요청에 `--retry-failed`를 지정하면 같은 키로 다시 시도할 수 있습니다. 결과 불명 상태 자체는 이 옵션으로 재시도할 수 없습니다. 복구 이력은 SQLite `events`에 기록됩니다.

`unknown` 상태에서는 같은 계정으로 `lookup`을 사용할 수 있습니다. 강제 종료로 `running/submitted` 상태가 남았으면 라이브러리는 잠금을 유지하므로 우체국 웹 화면에서 직접 확인합니다. PID가 재사용되었거나 호스트 이름이 바뀌어 원래 실행 주체의 종료를 확정할 수 없는 경우 복구가 차단될 수 있습니다. 이때 DB를 삭제하거나 잠금을 강제로 해제하지 말고 운영 환경과 프로세스 기록부터 확인하세요.

## 주문 DB와 맞추기

외부 접수 뒤 주문 DB 업데이트에 실패해도 같은 작업 키로 다시 실행하면 성공 결과를 재사용할 수 있습니다. 따라서 키를 매 실행마다 새로 만들지 말고 주문과 작업 종류별로 고정해서 보관하세요. `reserve:order-123:1`과 `cancel:order-123:1`처럼 작업을 구분합니다.

Journal 백업·복원은 모든 관련 프로세스를 중지하고 수행하세요. 성공 이력이 빠진 오래된 백업을 그대로 재가동하면 중복 방어가 사라집니다. 실제 우체국 내역과 먼저 대조해야 합니다.

## 배치 중단 후 확인

결과 JSON/CSV의 `key` 또는 `batch:reserve:배치ID:작업ID`로 건별 기록을 확인합니다. 같은 계정과 journal을 지정하세요.

```sh
node bin/epost.js history --status unknown --env-file .env
node bin/epost.js operation batch:reserve:shipment-001:order-002 --env-file .env
```

`INPUT_FILE`은 UTF-8·헤더·파일 크기를, `BATCH_VALIDATION`은 `issues`의 레코드 번호와 필드를 확인합니다. 각 잘못된 행의 첫 검증 오류를 모으며 입력 원문은 노출하지 않습니다. 이러한 전체 사전 검사 오류에서는 원격 작업이 시작되지 않습니다.

`OUTPUT_FILE` / 보고서의 `OUTPUT_FAILED`는 결과 파일 저장 문제입니다. 첫 저장에서 실패하면 아직 실행하지 않은 상태이지만, 이후 저장에서 실패하면 접수 성공 기록이 이미 있을 수 있습니다. 경로와 권한을 고친 뒤 같은 journal·배치 ID·행 ID로 다시 실행하세요. 보고서는 복구 기준 데이터가 아니며 SQLite journal이 작업 상태의 기준입니다.

결과 불명 건을 실제 사이트와 대조하고 복구한 뒤 원래 배치를 재실행합니다. 성공으로 복구된 건은 재사용합니다. 미접수로 복구된 건만 다시 처리하려면 `--retry-failed`를 함께 지정합니다. 남은 행은 순서대로 이어서 실행됩니다. 배치 전체를 되돌리는 자동 취소는 없습니다.
